# Battery telemetry processing contract (schema_v 2)

> SYNTHETIC DEMO. See `SYNTHETIC-DEMO.md`.

This document is the single source of truth for both implementations (`legacy/` Scala/Spark and
`rust-processor/`). The golden fixtures in `fixtures/` were written by hand from this document, not
generated by either implementation.

## 1. Topics

| Topic | Producer | Notes |
|---|---|---|
| `telemetry.battery.raw` | generator / vehicles | key = VIN (UTF-8), value = JSON (below) |
| `telemetry.battery.normalized` | legacy job | normalized schema_v 2 |
| `telemetry.battery.quarantine` | legacy job | rejected input |
| `telemetry.battery.normalized.shadow` | Rust processor (shadow mode) | same schema as `normalized` |
| `telemetry.battery.quarantine.shadow` | Rust processor (shadow mode) | same schema as `quarantine` |
| `telemetry.battery.rust-shadow.state` | Rust processor | compacted per-VIN state changelog (internal) |

In shadow mode the Rust processor writes to the `.shadow` topics so it never touches the legacy outputs.
Cut-over means pointing it at the non-shadow topic names (`OUTPUT_TOPIC`, `QUARANTINE_TOPIC`).

Consumer groups: legacy = `legacy-cg`, Rust shadow = `rust-shadow-cg`. Each group reads the full input
independently.

**Partitioning.** Producers MUST key records by VIN and MUST use the Java-client-compatible murmur2
partitioner (`partitioner=murmur2_random` in librdkafka clients). Outputs are keyed by VIN with the same
partitioner, so all records for one VIN stay in one partition on every topic.

## 2. Input record (`telemetry.battery.raw`)

```json
{"vin":"SYN-VIN-0007","event_id":"evt-…","ts_ms":1767225600000,"soc_pct":55.25,
 "pack_voltage_v":396.4,"pack_temp_c":21.37,"cell_delta_mv":12.7,"firmware":"bms-4.2.1",
 "location":{"lat":<number>,"lon":<number>}}
```

| Field | Required | JSON type | Rule |
|---|---|---|---|
| `vin` | yes | string, non-empty | must equal the Kafka record key |
| `event_id` | yes | string, non-empty | dedupe key (within a VIN) |
| `ts_ms` | yes | integer (no fraction, no exponent) | 0 ≤ ts_ms ≤ 253402300799999 |
| `soc_pct` | no | number | 0 ≤ soc_pct ≤ 100 (inclusive) |
| `pack_voltage_v` | no | number | passed through (within the decimal range below) |
| `pack_temp_c` | no | number | −40 ≤ pack_temp_c ≤ 80 (inclusive) |
| `cell_delta_mv` | no | number | — |
| `firmware` | no | string | passed through |
| `location` | no | object `{lat:number, lon:number}` | −90 ≤ lat ≤ 90, −180 ≤ lon ≤ 180 |

For an optional field, absent and JSON `null` mean the same thing. Unknown extra fields are dropped.

## 3. Validation

Checks run in this order. The **first** failing check sets the record's `error_code`, and the record
goes to quarantine.

1. Value is not valid UTF-8 JSON, or the top-level value is not an object → `MALFORMED_JSON`
   (this includes `NaN`/`Infinity` literals and truncated documents).
2. For each field in the order `vin, event_id, ts_ms, soc_pct, pack_voltage_v, pack_temp_c, cell_delta_mv, firmware, location`:
   - a required field that is absent, `null`, or an empty string → `MISSING_REQUIRED_FIELD`
   - a present field with the wrong JSON type → `INVALID_TYPE` (no coercion: `"55"` is not a number).
     `ts_ms` must be an integer literal; `1.7e12` and `1767225600000.0` are `INVALID_TYPE`.
     `location` must be an object whose `lat` and `lon` are both numbers; otherwise → `INVALID_LOCATION`.
   - **Decimal range.** A number in `soc_pct`, `pack_voltage_v`, `pack_temp_c` or `cell_delta_mv` must be exactly
     representable as ±m × 10^−s with integer 0 ≤ m ≤ 2^96 − 1 (79228162514264337593543950335) and 0 ≤ s ≤ 28,
     after dropping trailing fractional zeros; otherwise → `INVALID_TYPE` (for `location.lat`/`lon` →
     `INVALID_LOCATION`). So `1e30` and `1e-29` are rejected; `79228162514264337593543950335` and
     `1.500000000000000000000000000000` are accepted. This is a 96-bit decimal range, far outside any valid
     telemetry value; values are never rounded or clamped into it.
3. `vin` ≠ Kafka key → `KEY_MISMATCH`.
4. `ts_ms` outside the range → `INVALID_TS`.
5. `soc_pct` outside the range → `OUT_OF_RANGE_SOC`.
6. `pack_temp_c` outside the range → `OUT_OF_RANGE_TEMP`.
7. `lat`/`lon` outside the range → `INVALID_LOCATION`.

## 4. Normalization (output schema_v 2)

All arithmetic uses the **exact decimal value written in the JSON input**, not a binary float. "Half-up" means
round half away from zero.

| Output field | Derivation |
|---|---|
| `schema_v` | constant `2` |
| `vin`, `event_id` | copied |
| `event_time` | `ts_ms` as UTC ISO-8601 with exactly 3 fractional digits and `Z`, e.g. `2026-01-01T00:00:00.000Z` |
| `soc_pct` | rounded half-up to 1 dp (`55.25 → 55.3`, `55.24 → 55.2`), or `null` |
| `pack_voltage_v` | copied unchanged, or `null` |
| `pack_temp_k` | `pack_temp_c + 273.15`, rounded half-up to 2 dp, or `null` |
| `cell_delta_mv` | rounded half-up to an integer (`12.5 → 13`, `12.4 → 12`), or `null` |
| `firmware` | copied, or `null` |
| `out_of_order` | boolean, see §6 |
| `location_enc` | present only when the input had a non-null `location`, see §5 |

Output key = `vin`. Output has exactly these keys: `schema_v, vin, event_id, event_time, soc_pct,
pack_voltage_v, pack_temp_k, cell_delta_mv, firmware, out_of_order` plus `location_enc` when applicable.
`ts_ms`, `pack_temp_c`, `location`, `lat`, `lon` never appear in output.

> **DEFECT-1 (legacy only, intentional, documented).** The legacy Spark job *truncates* `cell_delta_mv`
> toward zero (`12.7 → 12`) instead of rounding half-up. This contract specifies half-up; the Rust
> processor implements the contract. The shadow comparator classifies this diff as `DEFECT-1`, and it is the
> only allowed field mismatch.

## 5. Location encryption

- Algorithm: AES-256-GCM, 96-bit (12-byte) nonce drawn from a CSPRNG **per event**, 128-bit tag.
- Key: `LOCATION_ENC_KEY` = standard base64 of exactly 32 bytes. `LOCATION_ENC_KEY_ID` (default `local-dev-1`)
  is a label only and contains no key material.
- Plaintext: UTF-8 JSON object `{"lat":<number>,"lon":<number>}` holding the input decimal values. Byte-level formatting
  may differ between implementations; consumers compare the recovered values numerically.
- Associated data (AAD): UTF-8 `telemetry.location.v2|<n>|<vin>|<event_id>`, where `<n>` is the decimal UTF-8 byte
  length of `<vin>`. It ties a ciphertext to its record; the length prefix keeps the encoding unambiguous when an
  identifier contains `|`.
  A ciphertext copied into another record fails authentication.
- Wire format:
  ```json
  "location_enc": {"ciphertext":"<base64(ciphertext || 16-byte tag)>","nonce":"<base64(12 bytes)>","key_id":"local-dev-1"}
  ```
- Plaintext coordinates MUST NOT appear in output, quarantine, logs, or committed fixtures.
- Startup: both processors **hard-fail** (non-zero exit, before consuming anything) when `LOCATION_ENC_KEY` is missing,
  is not valid base64, or does not decode to 32 bytes.

## 6. Ordering, dedupe, out-of-order

- **Ordering**: per-VIN order within a partition only. Records for one VIN are processed and emitted in input
  offset order. There is **no** global or cross-partition ordering guarantee.
- **Dedupe**: a *valid* record whose `event_id` matches one of the last **1000** accepted `event_id`s for the
  same VIN is dropped. It produces no output and no quarantine record. This dedupe applies only inside the
  processing boundary (the processor's own state). It does not cover producer-side duplicates that arrive
  outside that window.
- **Out-of-order**: a valid, non-duplicate record with `ts_ms` strictly less than the maximum `ts_ms`
  previously accepted for that VIN gets `out_of_order: true`. It is still emitted, and the maximum is not lowered.
  All other records get `out_of_order: false`.
- Invalid records do not touch per-VIN state. A repeated invalid record is quarantined again.

## 7. Quarantine record

```json
{"error_code":"OUT_OF_RANGE_SOC","vin":"SYN-VIN-0007","event_id":"evt-…",
 "source":{"topic":"telemetry.battery.raw","partition":3,"offset":1234},
 "original_payload":"{…original JSON with \"location\":\"[REDACTED]\"…}"}
```

- Key = the input Kafka key. `vin` and `event_id` are copied when they are present as strings, otherwise `null`.
- `original_payload` is the original value with the location removed:
  - parseable object: the value of every `location`, `lat`, `lon`, `latitude` or `longitude` key, at any depth
    (including inside arrays), is replaced by the string `"[REDACTED]"`, and the object is re-serialized compactly
    with key order preserved;
  - malformed input: in the raw text, any `"location": …` value (up to the matching `}` or the end of the text)
    becomes `"location":"[REDACTED]"`, and any remaining `"lat"`/`"lon"`/`"latitude"`/`"longitude"` numeric values
    become `"[REDACTED]"`.

## 8. Delivery semantics (Rust processor)

- **Boundary**: from Kafka input topic to Kafka output, quarantine, and state topics only.
- Mechanism: transactional (and therefore idempotent) producer. Each batch's outputs, its state-changelog records, and its
  consumer offsets (`send_offsets_to_transaction`, group `rust-shadow-cg`) are committed atomically. Offsets
  are never auto-committed.
- Guarantee within the boundary: after crashes and rebalances, a downstream consumer using
  `isolation.level=read_committed` sees every expected output exactly once. Aborted attempts may still be visible
  to `read_uncommitted` readers.
- Not claimed: exactly-once for any side effect outside Kafka, for `read_uncommitted` consumers, or across
  the legacy job (whose Kafka sink is at-least-once).

## 9. Logging

On a failure, processors log only `event_id` (sanitized to `[A-Za-z0-9_.:-]`, at most 64 chars) and
`error_code`. They never log raw payloads, coordinates, or key material.
